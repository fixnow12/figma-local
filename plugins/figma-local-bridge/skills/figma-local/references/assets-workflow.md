# Дизайн-система и готовые блоки

- Через `find_assets` ищи компоненты (`kind: "components"`), локальные стили (`styles`) и переменные (`variables`). Поиск по страницам по умолчанию ограничен текущей; `scope: "file"` загружает страницы файла без переключения активной. Учитывай `hasMore` и `nextOffset`.
- `library_collections` и `library_variables` возвращают метаданные доступных библиотечных Variables. Это строго два вызова: сначала `find_assets({kind:"library_collections"})`, затем для каждой нужной коллекции `find_assets({kind:"library_variables",collectionKey:"<key из результата>"})`. `collectionKey` обязателен; используй только ключ из достоверного результата или явно данного контекста, не угадывай его. Пустой список коллекций не разрешает вызывать `library_variables` без ключа. Поиск не импортирует ресурсы и не представляет полный каталог внешних компонентов или стилей.
- Пустой `library_collections` не доказывает недоступность компонентов или всех привязок Variables. Доступность экземпляра проверяется отдельно по известному `libraryKey` через `use_component` в разрешённом назначении; доступность уже существующей переменной — по её ID. До такой проверки сохраняй соответствующую возможность как неизвестную.
- Через `bind_variables` привязывай уже доступные в файле переменные по `variableId`; `null` снимает привязку. Сами переменные и их значения эта операция не редактирует.
- Не передавай `allowComponentChanges: true`, пока пользователь не подтвердил изменение оригинала компонента после предупреждения о влиянии на библиотеку. Обычные экземпляры и рабочие фреймы не требуют этого флага. Создание экземпляра предпочтительно копированию определения компонента.
- Правила индексов, границы структурных операций и примеры параметров описаны в [references/design-operations.md](design-operations.md). Прочитай этот файл перед клонированием, переносом или привязкой переменных.

## Импорт переменных библиотеки

Если подтверждён key исходной переменной, но в назначении нет её ID, используй `import_variables` с точным `fileKey` и массивом `variables: [{key, resolvedType, collectionKey?}]` (до 100 уникальных ключей). Инструмент импортирует ссылки в кэш назначения, не меняет значения или библиотеку. Результат `complete:true` содержит проверенные `variables[].id`, `key`, `resolvedType`, `collectionKey` и метаданные коллекций; используй эти ID в `bind_variables`, не выводи ID из ключа. При `partial` подтверждённые записи находятся в `blockers[0].evidence.variables`; набор не считается завершённым. После тайм-аута сначала проверь активную операцию через `get_status` того же файла. Импорт не откатывается удалением ресурсов.

## Проверка ключей уже доступных ресурсов

`resolve_resource_keys({fileKey, variableIds?, nodeIds?})` читает 1–100 точных ID из фактического дерева. Возвращает ключи переменных с типом и коллекцией, а для COMPONENT/COMPONENT_SET — библиотечный `key` отдельно от `semanticKey`. Ответ не доказывает публикацию локального компонента. Инструмент не импортирует ресурсы и не меняет холст; недоступные ID остаются `unresolved`. Полный ответ сохраняй как доказательство соответствия ID и key, не выводи key из строки ID.

## Точная замена вложенного instance

`swap_nested_components` доступен при capability `nested-component-swaps-v1`. Он изменяет только вложенные INSTANCE в недавно созданном рабочем instance; изменение оригинала библиотеки запрещено. До вызова нужны точные `fileKey/pageId`, root ID и semantic key, parent ID/key, root mainComponent ID/key и `creationOperationId` settled verified операции `use_component`, создавшей этот root. Передай стабильные `operationId` (UUID) и `operationKey`, полные `baselineNested`/`expectedNested` пути всех вложенных INSTANCE и 1–16 замен `swaps` в порядке от родителей к потомкам. Каждая замена содержит точные `childPath`, `fromLibraryKey`, уже доступные `sourceId/libraryKey`, `variant` и при наличии варианта `librarySetKey`. Инструмент сам ничего не импортирует.

Операция явно присваивает `mainComponent`: сбрасывает у заменяемого экземпляра наследуемые overrides. Поэтому выполняй её до восстановления согласованных свойств, текста, расположения и bindings. До первой записи проверяется достижимость всей конечной структуры; между заменами и после них читается полное дерево (до 1000 узлов). Потомки могут получить новые ID: отбрось старые descendant maps и выполни свежий полный `inspect_selection` перед следующими patches.

Журнал сохраняет исходные аргументы и не разрешает повторную отправку той же операции, включая после рестарта. После потери ответа вызови `get_operation_status` по сохранённому operationId. Продолжение допустимо только при точных аргументах, `settled:true`, `stage/state:verified`, `operationStatus:applied`, `resourceId` равном root и совпадающем свежем полном native read-back. `partial`, `unknown` и незавершённые операции блокируют дальнейшую сборку; автоматический rollback или replay отсутствуют. Обход квот и Starter-ограничений не допускается.
